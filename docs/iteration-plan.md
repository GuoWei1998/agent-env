# 迭代计划

**v1 冷创建已完成；v2 已实现双后端直连执行，待真实环境验收。** 当前运行说明见 [v2 验收](v2-run.md)。

每个版本都用同一条路径验收：**创建环境 → 等待可用 → 运行任务 → 释放资源**。这样无论是换后端还是优化启动速度，都能直接和上一版对比。

## 1. 路线图

| 版本 | 状态 | 做什么 | 怎么算完成 |
| --- | --- | --- | --- |
| v0 管理接口 | 完成 | memory 后端保存模拟记录；创建、查询、删除接口 | 不需要集群就能测完整生命周期；模拟实例状态明确为 `simulated` |
| v1 冷创建 | 完成 | 每个沙箱对应一个 Kubernetes Pod；Go 客户端可等待就绪，等待可取消 | 在测试集群跑通验收脚本：就绪后 `kubectl exec` 输出标记，删除后查询得到 404 |
| v2 执行与文件 | 下一步 | K8s 与本地 Linux Docker 共用模板、Go agent 及执行/文件协议；manager 启动时选择后端 | 同一 SDK 示例在两个后端上传工程、运行测试、下载报告并释放；能区分"客户端断线"和"命令退出码非零" |
| v3 恢复与隔离 | 规划 | PostgreSQL 保存创建意图、配额和租约；controller 核对记录与真实资源；沙箱超时自动回收、可续期；默认禁止出网；鉴权 | Pod 创建后、状态写回前重启服务，重试不产生第二个 Pod；租约到期与用户关闭同时发生时配额只释放一次；跨项目访问被拒绝 |
| v4 多集群 | 规划 | 登记各集群的能力和容量并据此选点；改用 client-go 共享 watch 观察就绪 | 双集群下停用一侧，验证选点和恢复；记录 Kubernetes API 请求量、首命令 P95、回收耗时 |
| v5 预热 | 规划 | 对比镜像预拉和空闲实例池；先固定水位，再按领取速率调整 | 同一空闲实例不会被领取两次；同样负载下比较冷启动、镜像命中、热池命中的首命令延迟和空闲成本 |
| v6 多运行时 | 规划 | 接入第二种隔离后端（gVisor / Kata / microVM）；按运行时和资源能力匹配请求 | 复用执行、文件、释放测试；不支持的组合在创建资源之前就返回明确原因 |

顺序背后的考虑：先让沙箱**能用**（v2），再让它**可靠且可以给别人用**（v3），然后才是**规模**（v4）、**速度**（v5）和**更强隔离**（v6）。快照、暂停与恢复依赖 v6 的运行时，排在其后。

## 2. v1 的契约与限制

**契约**

- 默认后端是 memory。加 `-provider kube` 才会操作集群，使用当前 kubectl context 和 `-namespace` 指定的命名空间。
- 创建返回 201 只表示 Pod 对象已建立。能否执行以状态 `ready` 为准。
- 删除返回 204 只表示 Kubernetes 接受了删除。真正回收完成以查询返回 404 为准。
- `WaitReady` 会一直等到就绪、失败或 context 结束，调用时要带超时。

**限制**

v1 没有后台对账、鉴权和独立数据面，因此只应在**个人开发集群、独立命名空间、本机回环地址**下使用。

| 限制 | 影响 | 应对 |
| --- | --- | --- |
| 创建请求中途断开 | 可能留下没有返回 ID 的 Pod | `kubectl -n agent-env get pods -l agent-env.local/managed=v1` 盘点后手动删除 |
| Pod 最长运行一小时 | 到期后变为 `terminated`，但对象不会自动删除 | 调用 DELETE 清理 |
| 没有出网限制和磁盘配额 | 不能运行不可信代码 | v3 补齐 |
| 没有执行接口 | 只能用 `kubectl exec` 进入沙箱 | v2 补齐 |

## 3. v1 运行与验收

**没有集群时**

```sh
go test -race ./...
```

覆盖 API 契约、Pod 清单内容、状态判定、查询与删除的选择条件、就绪等待与超时。kubectl 是假实现，所以**不验证**真实的 API Server、镜像拉取和调度。

**有集群时**

1. 确认 `kubectl config current-context` 指向测试集群，然后创建命名空间：

   ```sh
   kubectl create namespace agent-env
   ```

   当前账号需要在该命名空间内创建、读取、列举、删除 Pod，以及验收脚本用到的 exec 权限。

2. 启动 manager：

   ```sh
   go run ./cmd/manager -provider kube -namespace agent-env
   ```

   默认镜像是 `busybox:1.36.1`。可用 `-image` 换成其他镜像，要求包含 `sleep` 和 `echo`，并且能以非 root 运行。

3. 在另一个终端运行验收脚本（需要 curl、python3、kubectl）：

   ```sh
   bash scripts/smoke-kube.sh
   ```

   脚本通过管理 API 创建并等待就绪，用 `kubectl exec` 验证环境可执行，再删除并确认查询返回 404。中途失败时会尝试删除本次创建的实例。

## 4. v2 开发顺序与交付检查

以下是待实现任务。API 与状态语义以[总体设计 §6](design.md)为准；依赖、镜像与配置以[技术选型 §4](technology.md)为准。

1. **先做 agent 和模板。** 新建 agent 入口、exec 与 workspace 文件处理、模板 Dockerfile。先在 Linux 容器内验证 /readyz、非零退出码、显式取消、断线续读、二进制上传下载和越界拒绝，再发布固定摘要镜像。验收任务需要哪些工具，就在模板中明确安装哪些工具。
2. **打通 K8s 直连。** kube provider 使用新模板，安装 readinessProbe；增加端点解析、manager 路由接口和 SDK 访问层。SDK 从实际调用机器直接请求 agent，以首条命令成功验收，不借用 kubectl exec。
3. **接入本机 Docker。** 实现相同生命周期与端点解析，动态映射回环端口；复用步骤 2 的 SDK 示例和模板。测试用例只换 manager 的启动配置，不出现 docker exec 或客户端自行探测容器 IP。
4. **验证网络边界。** 让 SDK 只能访问 manager、不能访问沙箱网段：此时直连应在 deadline 内报告连接失败，不能误判为进程已退出。若该拓扑在本轮交付范围，共享 gateway 上线后用同一 SDK 和任务重跑；否则保留测试场景与路由契约，把 gateway 单独列为后续增量。
5. **双后端验收。** 各跑一次创建 → agent 就绪 → 上传工程 → 执行 → 下载并比对报告 → 删除至 404。各测一次错误凭据、过期路由、沙箱 A 的凭据访问 B、执行超时和上传中断。记录后端、模板 digest、SDK 所在网络与结果。无真实集群或 Docker 时只报告契约测试结果，不代替这一项。

v2 不做请求级自动选后端、多集群调度、持久化租约和自建镜像仓库。v1 的 smoke 脚本保留为底层排障工具，不能代替 v2 的 SDK 验收。
